API Overview & Authentication
Gautrain Transit Timetable Layer Contract

Welcome to the formal API contract and reference manual for TrainTimesAPI v1. This interface mediates between mobile client requests and the upstream Gautrain timetable microservices. To ensure low-latency performance and prevent upstream IP blocking, the API has a robust, layered, thread-safe caching system with telemetry indicators built directly into every envelope.

Base URL

environmentHost URL Configuration
Production URL:  https://your-production-server.com
Development URL: http://localhost:9292

Authentication Contract

Every call to a protected /v1/* endpoint requires authorization via a customized HTTP request header. The server performs a constant-time secure string comparison to ward off timing disclosure vulnerability attacks.

Header Key Type Description Contract Failure Code
X-Api-Key String Your secure API secret token (configurable in server environment as API_KEY). 401 Unauthorized (unauthorized)
🛡️ Security Constraint
Failure to supply the X-Api-Key header or submitting a value mismatch results in an immediate 401 Unauthorized response wrapper without hitting any upstream client endpoints. The /health endpoint is intentionally exempt from authentication.

Endpoints — Dynamic Timetable
GET /v1/journeys
GET Query itineraries and fares between stations

Fetches real-time, optimized journeys between any two Gautrain stations. Includes support for opaque token pagination and optional geospatial geometry polylines for high-fidelity routing displays.

Query Parameters

Parameter Constraint Description
from Required Slug identifier of departure station (e.g. rosebank). Must be in Station::VALID_SLUGS.
to Required Slug identifier of arrival destination station (e.g. marlboro). Must not match from.
after Optional Opaque pagination cursor token returned from a previous response's next_cursor field. (Base64 URL-Safe).
include Optional Enables extra payload details. Comma-separated list. Set to polylines to populate coordinates inside itinerary legs, and/or intermediate_stations to populate intermediate stops inside legs.
include_intermediate Optional Enables intermediate stops if set to true. Equivalent to including intermediate_stations in include.
requested_time Optional ISO 8601 timestamp (e.g. 2026-06-12T12:00:00+02:00) to evaluate journeys starting from a specific day/time. Defaults to current server time.
arrive_by Optional ISO 8601 timestamp (e.g. 2026-06-12T12:00:00+02:00) to perform a reverse-chronological search. The API will simulate backwards pagination and return the 5 trains arriving immediately before this time. This overrides requested_time and after parameters.

Response Caching lifespan (Cache-Control max-age)

The Cache-Control header's max-age value updates dynamically to reflect peak commute frequencies in South Africa Standard Time (SAST):

  • Morning/Afternoon Peak (Mon–Fri 06:00–09:00, 15:00–18:30 SAST): max-age=15
  • Weekday Off-Peak: max-age=60
  • Weekends & Holidays: max-age=120
  • Paginated requests with after: no-store; these bypass server cache and return meta.cache.status = "live_pagination".

⚠️ Pagination Cursor Constraint
Mobile clients must treat next_cursor as a sealed, opaque token. You should never attempt to decode or manipulate it. Simply capture the string and pass it back into the ?after= URL parameter to fetch the next page.
🕒 Timezone Alignment
The upstream Gautrain API operates strictly on South Africa Standard Time (SAST, UTC+2) and disregards timezone designators (such as Z). To ensure correct pagination sequence and chronological continuity, all UTC timestamp inputs (such as after pagination cursors) are translated into SAST (+02:00) before making the upstream query.

Metadata Booleans

Field Type Description
transfer_required Boolean True if any itinerary requires changing trains (crossing lines) to reach the destination.
last_train_has_left Boolean True if the last train for the current day has already departed (i.e. all itineraries are for the following day or later).
last_call Boolean True if the first returned itinerary departs today, but subsequent ones depart tomorrow or later.
Performance Architecture
Caching & ETags
How downstreams track freshness and validate ETags

The meta.cache block is the single source of truth regarding the freshness of the payload. Mobile clients use this block to adjust their interface and avoid serving stale schedules without informing the user.

Cache Telemetry Block

jsonThe meta.cache envelope schema
  "cache": {
    "status":      "fresh" | "stale" | "live_pagination",
    "cached_at":   "ISO 8601 UTC timestamp",
    "age_seconds": Integer (seconds elapsed since caching),
    "ttl_seconds": Integer (allocated maximum freshness period)
  }
Attribute Type Purpose / Behavior
status String "fresh": Within TTL. Data is fully validated.
"stale": Past TTL. Upstream Gautrain is currently down. Served as a safe fallback.
"live_pagination": Served dynamically bypassing the cache for paginated requests (Page 2+). Ensures absolute chronological continuity during infinite scroll without hitting stale cache walls.
cached_at String When this data record was originally compiled and stored.
age_seconds Integer Elapsed seconds calculated on the server at request time. (Will be 0 for live_pagination requests).

Conditional GETs (ETags)

TrainTimesAPI supports Conditional HTTP Requests via SHA-256 ETags. This saves massive amounts of mobile bandwidth.

  • The server always includes an ETag header in its response.
  • Mobile clients should cache this tag and append it to subsequent requests via the If-None-Match header.
  • If the timetable hasn't changed, the server instantly halts and responds with an empty 304 Not Modified body.

Rate Limiting
Token-bucket quota enforcement

To prevent API abuse and backend cascading failures, TrainTimesAPI implements a strict sliding-window Token Bucket rate limiter tied to your X-Api-Key.

Current Quota: 60 requests per rolling 60-second window.

Standard Rate Limit Headers

Every response (success or error) contains tracking headers so your client can preemptively throttle network tasks before hitting the limit:

Header Example Value Meaning
X-RateLimit-Limit 60 The maximum number of requests your key is allowed within the rolling time window.
X-RateLimit-Remaining 59 How many tokens remain in your bucket right now.
X-RateLimit-Reset 24 Seconds until your bucket is completely refilled to the maximum limit.

Exceeding the Limit

If you exhaust your tokens, the API instantly rejects the call with an HTTP 429 Too Many Requests problem document. It will also append a standard Retry-After header telling the client exactly how many seconds to pause before trying again.

Errors & Codes Reference
Structured API errors adhering to RFC 7807 Problem Details

TrainTimesAPI uses semantic, consistent HTTP status codes paired with detailed JSON objects that strictly adhere to the IETF RFC 7807 Problem Details for HTTP APIs schema. They are served with the application/problem+json content type.

Standard Error Codes

Code Type (Suffix) HTTP Status Triggers & Context
missing_parameter 400 User omitted from or to parameters.

invalid_cursor 400 The supplied after parameter failed to decode as a valid URL-safe Base64 token.
